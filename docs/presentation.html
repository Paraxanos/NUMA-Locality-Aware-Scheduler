Slide 3 — Scheduling Mechanism & Locality Dealing

Significance Gate: Task footprint D > LLC / core? Small tasks → local execution; significant tasks → locality work dealing.

Algorithm 3: Locality-Aware Work Dealing
  For each tile X ∈ [0, 63]:
    cost(X) = Σ (D[i] / line_size) × latency(X, i)
  Route task to argmin(cost) tile queue

Shadow Index (N-B): Lock-free ring buffer of k=8 tasks per node. Idle workers peek nearest tiles, select argmin(local_cost), then steal — never random.

Adaptive Radius (N-C): Radius r increases on failed steals (EWMA); decreases on successful steals. Keeps search bounded: d ∈ [1, max_diameter].

Left: NUMA Figure 7 reproduction. Right: TILEPro64 56-run results.

Why It Fails

  • Regular (Map): Footprint evenly distributed; locality distributes work naturally → 19.0% faster.
  • Irregular (SparseLU): DAG creates unbalanced footprints; locality-only funnels tasks onto a single node, leaving 23/24 NUMA nodes idle → queue clumping → 15.1% slower than naive WS.
  • Core Lesson: Data locality without load balancing is worse than no locality at all.

TILEPro64 Corroboration — Map LA+Coarse: 80.3% lower comm cost (1.31M vs 6.67M), 39.3% faster (170K vs 281K cycles), 0 steals required vs 63 for WS. Coarse assigns entire buffer blocks to single tiles (reduced overhead); Fine stripes each cache line (better locality for fine-grain access, but more overhead).

Slide 4 — Speaker Notes: "On NUMA, the paradox: locality scheduling reduces SparseLU's communication cost by 26.7% to 0.733, yet execution time increases 15.1% to 1.151. The cause is queue clumping: locality-only places every task onto the same home node; 23 of 24 workers sit idle. For regular workloads like Map, locality is unambiguously good. For irregular SparseLU, it is worse than naive work-stealing. The TILEPro64 simulator confirms this: Map sees 80.3% comm reduction and 0 steals; the irregular sparse patterns create similar imbalance." (Point to each metric as spoken.)

Slide 5 — The NOVA / ALLoC Solution & Key Conclusions

N-A · N-B · N-C — Adaptive Co-Scheduling

N-A (Load-Aware Dealer): score(q) = α · cost_norm(D,q) + (1−α) · occ_norm(q) — dynamically blends communication cost with queue backlog to prevent clumping.

N-B (Task-Level Stealing — Shadow Index): Lock-free ring buffer of k=8 tasks per node. Idle workers peek nearest tiles, steal task with minimum local_comm_cost, never random.

N-C (Adaptive Vicinity Radius): Radius r adjusts via EWMA: r↑ on failed steals, r↓ on successes. Keeps search bounded: d ∈ [1, 14] (NUMA) / d ∈ [1, max_mesh] (TILEPro64).

Examiner Q&A — Three Key Questions (Prepared Answers)

Q1 — Why build TILEPro64 simulator instead of real hardware?
A: TILEPro64 was discontinued; software model provides reproducible, deterministic 8×8 mesh with Manhattan latency, without hardware drift.

Q2 — Why does WS have 63 steals and LA+Coarse 0?
A: WS: Tile 0 creates all tasks, others steal randomly → 63 steals. LA+Coarse: dealer places each task on its data home tile; 0 remote steals required.

Q3 — How does NOVA prevent synchronization overhead?
A: Double-buffered pointer swap: hot path uses lock-free atomic loads; control plane updates statistics every 64 ops via CAS. Zero locks on execution path.
